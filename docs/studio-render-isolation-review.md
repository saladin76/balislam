# Studio — عزل الرندر وسلّم مراجعة الصوت والصورة (مسودة تطوير 2026-11-07)

> **النطاق:** فرع `work/studio-render-isolation-20261107` فقط، لقنوات `balislam` و`dafatir-alzaman` و`zubdat-alkutub`. هذا مستند فحوص ولا يمنح اعتمادًا، ولا يفعّل Master أو نشرًا أو Vercel. العقد الملزم: `docs/studio-production-stage-contract.md`.

## 1. ملكية الوسائط ونتائج الرندر

- هوية الرندر مشتقة من **مسار السكريبت الحقيقي**: `_render/<channel>/<episode-folder>/<content-sha256>/`. لا يكفي رقم الحلقة `001`؛ قد يتكرر في القنوات الثلاث.
- تنسخ الملفات إلى مجلد مرحلي خاص بالمحاولة `.stage-*`، ثم تحسب SHA-256 من **النسخة المنسوخة** لكل ملف، وتُنشئ لقطة ثابتة بنقل ذري. لا تُحذف لقطة قديمة لإعادة التحضير، حتى إذا بدأ رندر جديد لنفس الحلقة أو فشل أو أُلغي.
- يُسمح بإعادة استعمال لقطة متطابقة فقط بعد التحقق من فهرسها وبصمات الملفات. يمنع اسم ملف غير آمن أو رابطًا رمزيًا أو محاولة الكتابة خارج المجلد المملوك. ينظَّف المجلد المرحلي الخاص بالمحاولة فقط، لا لقطات زملائها.
- حزمة Remotion الخاصة بالحَلقة تضم الأصول العامة المشتركة (مثل الخطوط)، ولقطة الوسائط المسموح بها **لهذه الحلقة وحدها**؛ لا تضم وسائط قنوات أو حلقات أخرى الموجودة في `public/_render`. تُزال نسخة مجلد `public` المؤقتة بعد نجاح المهمة أو فشلها.
- ملف `*.mp4` النهائي لا يُستبدل إلا بعد نجاح الرندر وتنظيف البيانات الوصفية. لكل محاولة `*.rendering.mp4` مستقل؛ ولكل مهمة في `RenderPool` ملف `*.part-<uuid>.mp4` مستقل محفوظ الملكية في سجل الاستعادة. الإلغاء أو الانهيار لا يحذفان ناتج مهمة أخرى أو النسخة السليمة السابقة.
- لا يجوز حذف النسخ التاريخية من `_render` بالاعتماد على عمرها أو رقم الحلقة وحده. أي سياسة تنظيف مستقبلية تحتاج إثبات عدم وجود عملية Remotion تستخدمها، وتدخل ضمن مهمة ملفات `/tmp` المنفصلة، لا هذه المهمة.

## 2. مراحل الرندر المعتمدة

| المرحلة | التوقيت | ما يسمح به |
| --- | --- | --- |
| السكريبت والمصادر | تقديري | النص يحدده صاحب المشروع؛ فحص المراجع والآيات وملاحظات الاختلاف دون أي تصحيح تلقائي |
| Storyboard المرئي | تقديري | صور ولوحات وPDF ومراجعة كل مشهد؛ لا بدء للحركة النهائية |
| النبرة والصوت | تقديري حتى تُعتمد الحلقة الصوتية **كاملة** | عينات وملفات الصوت ومراجعة كل مقطع ثم الاستماع المتصل والتوقيع البشري |
| Motion | توقيت الكلمات من الصوت المطابق **بعد** اعتماد الحلقة الصوتية | إعادة استعمال القوالب والرسومات والكادرات والأصول الموجودة؛ إعادة ضبط لحظة ظهور الكلمات والأحداث والانتقالات، مع احترام سكون الآيات والأذكار |
| مراجعة AV | الصوت مع الصورة بسرعة 1× | فحص زمني متصل، لا مجرد عينات أو إطارات منفصلة؛ تسجيل إصلاحات المشاهد بالوقت |
| Master | بعد موافقة المالك | لا يصنعه اجتياز CI، ولا اكتمال معاينة، ولا وصول ملف إلى Drive؛ الموافقة على نسخة ذات بصمة وإصدار معروفين |

**تنفيذ حماية التوقيت:** `voiceTimingMode` يقرأ سجل اعتماد **كل** مقاطع MP3 والاعتماد البشري للاستماع المتصل للحلقة؛ ما لم يثبت كلاهما على البايتات الحالية يُمرَّر `timingMode: "estimated"` إلى Remotion، فلا تستهلك حركة كلمات الراوي توقيتات خامًا غير معتمدة. بعد الاعتماد فقط `timingMode: "approved"`، دون إنشاء موافقة جديدة. قد يُحافظ مشهد تجريبي على طول مقطع صوت متوفر كي لا يقطعه؛ لا تُفسَّر تلك المدة على أنها توقيت حركة نهائي. آلية الآيات والتلاوات المرخّصة أو المجلوبة كما هي حاليًا؛ لا يغيّر هذا الفرع اختيارات القارئ أو مصدر التلاوة أو اعتمادها.

## 3. فحوص آلية قبل أي تجربة

```bash

```

يجب التحقق من: التوازي بين القنوات والحلقات مع اسم وسيط مكرر، رندرين للحلقة نفسها بنسختين، الإلغاء قبل النسخ وأثناءه، استعادة `RenderPool` بعد انقطاع، فساد وسيط قديم، مسار Remotion المعزول، صور عربية/لاتينية، وحركة الراوي قبل/بعد اعتماد MP3. اختبارات Node **لا تثبت** أن متصفحًا أو هاتفًا عرض الحلقة بصريًا، ولا تحل محل اختبار Mac المنعزل.

## 4. بوابة المراجعة المتكاملة وتجربة الهاتف — **تحتاج تنفيذًا بشريًا**

قبل اقتراح Master، يُسجَّل للحلقة والإصدار والبصمة والاتجاه الأفقي/الرأسي:

1. تشغيل نسخة المعاينة **كاملة مرة واحدة بسرعة 1×** بالصوت والصورة؛ فحص الانتقالات ووصل المشاهد، تزامن الكلمات والأحداث، نهاية جمل الراوي، بداية/نهاية التلاوات واحترام السكون المقصود، والتباين وحجم الخط وعدم قص العناصر. سجل أي خلل بـ `channel / episode / scene-id / hh:mm:ss / orientation / before-after`.
2. تجربة **هاتف حقيقي** للوضع الرأسي `9:16` ومعاينة مشغّل الهاتف (ويُفضّل Android وiOS)، مع معاينة أفقية `16:9`: الهوامش الآمنة، عدم قطع العناوين والترجمة، وضوح الفونت والتشكيل واتصال الحروف، عدم تغطية واجهة المنصة للكلمات أو الآيات، وضوح الصوت، وعدم ظهور شاشة سوداء أو تجمّد.
3. الرجوع إلى لقطة Storyboard والصوت المعتمدين عند أي اختلاف. لا يُعتبر مرور فحص الإطارات الساكنة وحده، أو فحص CI، أو رفع معاينة، موافقة AV أو اعتماد Master.
4. توثق نتيجة كل فحص بقيم `PASS` أو `FAIL` أو `NOT_RUN`، واسم المراجع وتاريخ المراجعة وبصمة الفيديو؛ الافتراضي الآن **`NOT_RUN`** حتى تتم التجربة فعليًا. لا تكتب برمجيًا حالات `AV_REVIEW_APPROVED` أو `MASTER_OWNER_APPROVED`.

## 5. حدود هذا التغيير

- لا تعديل لمصدر نص القرآن/التلاوة، أو سكريبتات الحلقات، أو هوية القنوات.
- لا رندر إنتاجي، ولا اعتماد Master، ولا نشر، ولا دمج، ولا Vercel، ولا مساس بـ`main` أو `~/balislam` على Mac.
- عند فشل بوابة Mac أو تجربة الهاتف تُسجل الحالة `BLOCKED` ويظل PR مسودة.
