# مسودات رسائل التسليم للمحادثات الست — Studio vNext

**التاريخ:** 7 نوفمبر 2026. **الحالة:** مسودات للتثبيت بعد الاختبار المعزول وموافقة صاحب المشروع على إصدار Studio vNext. لا ترسل على أنها تعليمات إنتاج نافذة قبل ذلك. القواعد الدائمة في `docs/studio/production-workflow-vnext.md` وصفحات أدلة القنوات الثلاث `09-workflow-vnext.md`.

## قواعد مشتركة لكل عامل

المشروع `saladin76/balislam`. القنوات: `balislam` (بالإسلام)، `dafatir-alzaman` (دفاتر الزمن)، `zubdat-alkutub` (زبدة الكتب). ست مراحل لا تُتجاوز: (1) السكريبت والمصادر، (2) Storyboard والتكوينات، (3) التعليق الصوتي الكامل، (4) مزامنة الحركة، (5) مراجعة الحلقة كاملة 1× وتجربة الهاتف، (6) اعتماد **الملف النهائي نفسه** من صاحب المشروع ثم النشر.

صاحب المشروع **يكتب الآيات بنفسه داخل السكريبت**. قارن نصها بالرسم والتشكيل مع المصحف المعتمد دون جلب نص بديل أو تعديل آلي. لا تفترض أن كاتب النص هو مؤدي التلاوة. التلاوة اختيار مستقل يخضع للحقوق والاستماع والمراجعة؛ يجوز عرض الآية صامتة عندما لا يُختار لها صوت. لا يستنتج النظام موافقة من نجاح GitHub أو وجود ملف.

كل عامل يلتزم بفرعه المخصص، يُسلّم Draft PR بفحوص صريحة وتقرير حدودها، ويُحيل التغييرات المشتركة إلى منسق التكامل PR #78. ممنوع المساس بـ`main` أو نسخة Mac الإنتاجية أو تعديل ملفات الحلقات تلقائيًا أو نشر Master أو استخدام Vercel. اختبارات Mac فقط داخل مسار عمل معزول، والمراجعة البصرية/السمعية البشرية منفصلة عن الاختبارات الآلية.

## 1 — رسالة فريق P0: الملفات المؤقتة وسلامة الاختبارات

**مرجع العمل:** PR #72، الفرع `work/studio-p0-temp-20261107`. **مالك النطاق:** `scripts/gate.mjs` و`scripts/verify-studio-temp-leaks.mjs` واختبارات `tests/` الخاصة بحياة المجلدات المؤقتة. لا تنقل تعديلات القرآن أو الصوت أو الرندر إلى فرع P0.

مهمتك: ضمان أن الاختبارات لا تنسخ حلقات الإنتاج وأصولها الكبيرة إلى `/tmp`، وأن الموارد التي أنشأتها الاختبارات نفسها تُنظّف عند النجاح والفشل والإلغاء ومع التوازي. لا تُحذف مجلدات الآخرين أو ملفات Remotion وwebpack لمجرد أنها قديمة أو تحمل بادئة مشابهة. سجّل البصمات/الحجوم قبل وبعد تكرارات الاختبارات في مساحة معزولة، واختبر أن `git status` وملفات الحلقات لم تتغير.

**نقطة التكامل:** ملفات اختبارات مشتركة مع #73 و#76؛ لا تستبدل الاختبار الأحدث بنسخة تنظيف أقدم. افتح طلبًا لتعديل محدد إن كان التعارض في ملف يملكه فريق آخر. فحوص GitHub ليست بديلًا عن قياس قرص Mac عمليًا.

**التسليم:** قائمة الملفات المنتقلة، اختبار الفشل/الإلغاء/التوازي، استهلاك القرص الحقيقي، وسبب أي تسرب متبقٍ؛ مع حالة `CI` و`Studio parity` والقيود غير المفحوصة.

## 2 — رسالة فريق P1: PDF العربي

**مرجع العمل:** PR #71، الفرع `work/studio-p1-arabic-pdf-20261107`. **مالك النطاق:** `scripts/studio-storyboard-pdf.mjs` واختباره.

مهمتك: حفظ حروف العربية المتصلة والتشكيل دون فصل الأحرف، وضبط اتجاه RTL والمعرّفات اللاتينية وعناوين الفصول وأغلفتها. لا يُقص نص في صفحات Storyboard أو ملحقاته. حافظ على عدد المشاهد والملحقات المعتمدة للفصلين السابقين من «دفاتر الزمن»، واختبر الخطوط وهوية القنوات الثلاث دون إضافة تغيير على نص الحلقة أو اختيار الآيات.

**نقطة التكامل:** يُستخرج محتوى بطاقة القرآن من السكريبت بعد المقارنة، لكن PDF لا يملك حق تعديل النص أو اعتماد Storyboard. ينبغي فحص التصدير الفعلي عبر Chrome على Mac معزول، لا الاكتفاء بفحص HTML أو Unicode.

**التسليم:** نموذج PDF من قناتين على الأقل والفصلين المعنيين، تقرير الصفحات ولقطات مواضع النص والتشكيل والقص، وفحوص مقارنة الأصول السابقة.

## 3 — رسالة فريق القرآن والصوت

**مرجع العمل:** PR #76، الفرع `work/studio-quran-audio-20261107`. **الملفات الأساسية:** `src/quran/scriptText.ts` و`src/quran/audit.ts` و`src/quran/manualAudio.ts` و`src/voice/review.ts` ومكونات إدخال ومراجعة السكريبت.

مهمتك: اعتبار السكريبت الذي كتبه صاحب المشروع المصدر الوحيد لنصوص الآيات، والتحقق من المراجع والتشكيل على المصحف وإظهار الفروق للمراجعة الشرعية الصريحة؛ لا تعيد إدخال الآيات في نافذة أخرى كمصدر مستقل ولا تصححها تلقائيًا. حافظ على نسبة مصدر الترجمات التاريخية؛ لا تنسب القديم إلى إدخال يدوي. لا تفترض أن صاحب المشروع يتلو الآيات لمجرد كتابتها.

للصوت: تُراجع عينات النبرات ثم التسجيلات كاملة، ويُلزم الملف القابل للرندر باعتماد الصوت، والنص الحالي، والملف الصوتي الحالي ببصمة صحيحة، ودليل حقوق الاستخدام. فساد MP3 أو تغيير حركة واحدة في السكريبت يعيد الاعتمادات المتأثرة. لا تبدأ الحركة النهائية قبل اعتماد التعليق كاملًا.

**نقطة التكامل:** جمع الملفات الصوتية ضمن `src/plan/collect.ts` مسؤولية الرندر/التكامل لا هذا الفريق. لا تكتب في ملفات حلقات الإنتاج ولا تستبدل مصدرًا مرخّصًا دون قرار.

**التسليم:** تقرير مقارنة الآيات، بيانات المصدر/الحقوق، اختبار فساد الصوت وتغير النص، وقائمة مقاطع وتسجيلات تحتاج تدخل المالك.

## 4 — رسالة فريق الرندر والعزل

**مرجع العمل:** PR #73، الفرع `work/studio-render-isolation-20261107`. **مالك النطاق:** `src/plan/collect.ts` و`src/plan/renderStage.ts` و`src/render/` وملفات Remotion ذات الصلة.

مهمتك: فصل الوسائط بحسب القناة والحلقة وبصمة المحتوى، وحماية الناتج القديم أثناء المحاولات المتوازية والفشل والإلغاء، ومنع محو ملف عامل آخر. تُجهّز الوسائط المدققة بإصدارات ثابتة، ولا يتم دمج ملفات قناة في أخرى.

الزمن قبل اعتماد التعليق كاملًا **تقديري**. بعد الاعتماد تُضبط الحركة والكلمات والانتقالات على الصوت الفعلي، مع إعادة استخدام الأصول المناسبة للمشهد. بطاقة آية صامتة لا تفرض عليها تلاوة تلقائية؛ التلاوة المستخدمة فعلًا تحتاج مصدرًا وحقوقًا موثقين.

**نقطة التكامل:** البوابات الجديدة تمنع الرندر الحركي النهائي قبل اعتماد الصوت، ثم تمنع Master قبل المراجعة المتكاملة. لا تستخدم `allowUnreviewed` أو CLI لتجاوز تلك البوابات، ولا تفترض أن الرندر ناجح بصريًا لمجرد نجاح اختبارات Remotion.

**التسليم:** اختبار العزل والتوازي والإلغاء، رندر مراجعة مصغر في Mac معزول إن كان مصرحًا، جودة التوقيت، وفحص الهاتف الأفقي والرأسي والمشاهدة المتصلة 1×.

## 5 — رسالة فريق محرك الاعتمادات

**مرجع العمل:** PR #77، الفرع `work/studio-workflow-gates-20261107`. **مالك النطاق:** `src/workflow/gates.ts`، `src/workflow/store.ts` واختباراتهما. **تكامل الخادم بعد جمع الفروع:** `src/workflow/artifacts.ts` و`src/workflow/server.ts` في PR #78.

مهمتك: منع تجاوز التسلسل الرسمي بقرارات بشرية صريحة وحالة دائمة لكل قناة وحلقة. كل قرار يحمل هوية المالك من الخادم وتاريخه وإصدار المحتوى وSHA-256 وملاحظة وسجل أحداث؛ تغير أي مصدر يبطل نفسه والمراحل التابعة، ولا تنقذ إعادة البايتات القديمة موافقة أبطلت.

تحقق من التصريح والهوية على الخادم؛ لا تقبل `role=owner` أو `approved=true` أو بصمة ملف يرسلها المتصفح بوصفها إثباتًا. ربط واجهة Studio قراءة حالة فقط لا يصدر موافقات ضمنية. بوابة Master تقارن **بايتات الملف النهائي**، لا `status.json` القديم أو حجم/mtime، وتتأكد من وجود المسارين السمعي والبصري.

**نقطة التكامل:** أسماء المحرك `av_review` و`needs_reapproval` تقابل `review` و`reapproval_required` في الواجهة. لا تنقل `workflow-approvals.json` إلى قناة أخرى، ولا تمنح موافقات للعناصر القديمة بأثر رجعي.

**التسليم:** اختبارات التصريح والختم والتلاعب والتوازي وتغيير المصادر، وخريطة لكل مسار CLI/API يحتاج رفضًا قبل الإنتاج، مع توضيح أي سباق تعديل/رفع باقٍ.

## 6 — رسالة فريق واجهة Studio

**مرجع العمل:** PR #74، الفرع `work/studio-ui-workspaces-20261107`. **مالك النطاق:** الواجهة والتنقل وCSS واختبارات العمل؛ **تكامل vNext:** `app/src/workspace/WorkflowOwnerControls.tsx` و`WorkflowApprovalDetails.tsx` و`app/src/tabs/PublishTab.tsx` داخل PR #78.

مهمتك: فصل غرف العمليات والمراقبة عن إدارة القنوات الثلاث وعن مساحة إنتاج الحلقة وعن الأدوات. اعرض الست مراحل وملاحظاتها وشواهدها بنظرة واضحة، وامنح معاينات Storyboard والمشاهد والفيديو المساحة اللازمة. حافظ على كل ميزة سابقة دون إدخال منطق يمنح اعتمادًا لمجرد توافر ملف أو اكتمال نسبة.

حالة الاعتماد الحقيقية تأتي **فقط من API المحرك** بعد التحقق من الملفات. اعرض المعتمد والتاريخ وإصدار المحتوى، وتأكد من أن `needs_reapproval` تظهر «تحتاج إعادة اعتماد». أزرار المالك ترسل أفعالًا مستقلة `submit` ثم `approve` برمز محلي، مع ملاحظة وتأكيد الاستماع/المشاهدة عند الحاجة؛ لا يُخزن الرمز في المتصفح.

**نقطة التكامل:** شاشة النشر لا تُظهر علامة «Master معتمد» بناء على حجم/mtime تاريخي فقط، وأي رفض للخادم لا يظهر كأنه حفظ ناجح. جرّب الشاشات الصغيرة والتنقل بلوحة المفاتيح والربط بالمشاهد والفيديو من كل قناة.

**التسليم:** اختبار تنقل ومكونات، تجربة Mac متصفح معزول، ملاحظات UX، وحالة اتصال API وحالات الاعتماد الحقيقية، دون رندر أو نشر إنتاجي.
